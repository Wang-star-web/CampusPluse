# AI 会话快照 · 2026-11-06（A00 阶段01增量：/api/sim/set 模拟配置 API）

> 如实记录当天开发会话，不补写、不美化。与当日 git commit 同日完成。

## 一、任务

阶段01 补充开发（不新增态势逻辑，只完善模拟器调试能力）：
1. 后端全局内存变量保存模拟器配置（crowd / entrance_available / main_route / support）；
2. `POST /api/sim/set` 修改配置（/docs 可调试），模拟器读取后端配置向外发数据，
   改配置无需重启 uvicorn，WebSocket 自动推送新数据到前端；
3. 前端顶部预设按钮【300】【500】【650】【750】【900】，点击调 /api/sim/set 写入对应参数包；
4. 硬约束：只修改原始模拟数据源，不做任何态势/impact/派生计算，按钮只改变原始观测值。

## 二、关键决策

1. **配置唯一入口改为后端内存 API，移除 sim_values.json 文件热读机制**（用户拍板）：
   单一事实来源，杜绝文件/接口两入口不一致；README 同步改为按钮+curl+/docs 三种等价改法。
2. **默认配置取 500 预设**（crowd=500、entrance_available=2、normal、support=10）：
   中位场景；support 默认值由旧文件的 12 变为 10（README 注明；support=12 仍可经 API 设置）。
3. **后端 POST /api/sim/set 刻意不直接发 MQTT**：页面变化必须走
   模拟器轮询 → MQTT → 后端 store → WS 链路，保证"页面变化必然来自数据源变化"验收不被旁路
   （实测传播延迟 1.8~2.2s）。
4. **模拟器冷启动未拉到配置前不发布任何消息**（无残留纪律）；运行中后端不可达则沿用上次配置
   继续发布，且告警只在状态切换时打印一次（防每 2s 刷屏）。
5. **配置合法性校验移交后端 pydantic Literal**（crowd/entrance_available/main_route/support 枚举），
   非法值 422 且存储不动；模拟器只做键存在性防御检查。
6. **前端按钮高亮为纯展示态**：按人群原始值相等比较，不产生任何业务值；卡片数值仍只由
   WebSocket 消息渲染（点击处理器绝不写卡片 DOM）。

## 三、AI 出错与纠正

1. **误杀 crowd 模拟器进程**：清理双 uvicorn 进程树时，把 PID 15972（实际是 crowd 模拟器）
   当成了 uvicorn worker 一并 taskkill——教训：kill 前必须完整查看每个 PID 的命令行再动手。
   纠正：重启 crowd 模拟器，链路恢复。
2. **curl 管道到 python 时中文 JSON 损坏**：curl 输出的 UTF-8 被 stdin 按 GBK 误读导致
   JSONDecodeError。纠正：改用 urllib 直连请求 openapi.json。
3. **环境排查：两个 uvicorn --reload 并存**（商店版 python 与 python.org 版各起一个 watcher），
   端口归属混乱（与"Windows 双 Python 环境"记忆一致）。纠正：两棵进程树全部停止，
   只保留一个干净的 --reload 实例。

## 四、验证结果（全部通过）

- `GET /api/sim/config` 默认返回 500 预设包；
- 5 个预设依次 POST，四对象值 1.8~2.2s 内全部匹配（750：750/1/2/normal/8；900：900/1/2/limited/8；
  300/500/650：2/2/normal/10），uvicorn 零重启；
- WebSocket 客户端实测：POST 750 后四对象增量 update 帧全部到达（页面无轮询、无手动刷新）；
- /docs OpenAPI 含两个新端点与 4 个 Literal 枚举；
- 422 五连测（crowd=999 / entrance_available=3 / main_route="blocked" / support=13 / 缺字段）
  全部 422 且配置不变；
- 后端宕机期间：mosquitto_sub 证实模拟器沿用最后配置持续发布（每 2s）；后端重启后配置回
  500 默认，四对象一个轮询周期内自动跟随恢复；
- grep 检查：变更文件无态势/impact/派生业务逻辑；sim_values/ALLOWED 残留仅存在于
  历史快照 2026-11-05.md（按纪律不改）。

# AI 会话快照 · 2026-11-06（同日第二次任务：A00 阶段02 证据层）

> 与上一部分同日的第二次开发任务，如实追加记录，不改动前面内容。

## 一、任务

1. SQLite 两张表：observations（业务事实）/ evidence（取证记录）；status ∈ ok/unavailable/error
   **只表示本次取证是否成功**；失败时 value_json=null，绝不伪造业务值、绝不把获取失败写成业务异常
2. MQTT 成功消息 → observations + evidence(ok) 双写；模拟器支持 ok/unavailable/error 模式切换，
   失败模式只新增 evidence、保留历史最后成功 observation
3. 接口：GET /api/history/{object_type}、GET /api/evidence/latest/{object_type}、GET /api/evidence/{evidence_id}
4. 前端证据追踪区：区分【最后成功确认的业务值】与【本次最新获取状态】
5. 不实现约束/派生结果/影响/态势/run_id

## 二、关键决策

1. **失败信号每周期连续上报**（用户拍板）：失败模式每 2s 发一条失败信封（observed_at/data 为 null
   + retrieval_status + error_message），后端每次落一条 evidence——像真实采集器持续重试一样记录
   每次取证尝试；qos0 丢失下周期自愈。官方指南允许的两种教学做法之一（数据源主动上报）。
2. **证据查看区扩展 index.html**（用户拍板）：与官方 2.6 目标效果一致（同一页同时显示两类信息）。
3. **信封 validator 在结构上禁止伪造**：retrieval_status 为 null → observed_at/data 必填；
   非 null → 二者必须为 null（不可能把失败改写成业务值）；error 必带 error_message、unavailable 禁带。
4. **evidence_role 统一 `current_fact`**（阶段05 词汇，前向兼容）；evidence_id = ev_{object_type}_{seq:03d}
   （官方示例格式；seq=表内计数+1，写入仅来自 paho 单线程，无竞态）。
5. **同事务双写**（官方不强制，自选更强保证）；DB 写失败只记日志不阻断 store.update（内存态是
   /api/current 的权威，持久化是最佳努力）。
6. **db.connect() 幂等建表**：消除"阶段01 MQTT startup 事件先于阶段02 建表事件"的启动顺序竞态。
7. **SimMode 用嵌套 pydantic 模型 + extra="forbid"**（裸 dict 不校验，会破坏 422 纪律）；
   mode 可选缺省全 ok、全量替换语义写进 docstring。
8. 前端徽章色（ok 绿 / unavailable 灰 / error 琥珀）只表达**取证运营状态**，业务值一律无色；
   动态字段（source/evidence_id/error_message 来自消息内容）全部 esc 转义防注入。

## 三、AI 出错与纠正

1. **T8 测试脚本计账失误**：断言 observations 只 +1，忽略了模拟器每 2s 也在持续发布并发消息。
   纠正：改用特征值（手工发 count=555，不在模拟器允许集内）精确定位唯一一对 observation+evidence。
2. **renderEvidence 用 innerHTML 拼接动态字段**：source/evidence_id/error_message 来自 MQTT 消息内容，
   存在注入风险。纠正：补 esc() 转义后仅保留静态徽章 HTML。

## 四、验证结果（全部通过）

- 建表：runs/observations/evidence 三表齐（与 Day1 同文件 backend/campuspulse.db）
- 双写：每对象 observations 行数 == evidence(ok) 行数（严格相等）；evidence_id 自 ev_{ot}_001 起
- 接口：history 倒序/limit 边界 422；latest/详情正常；未知 evidence_id 404；非法 object_type 422
- **核心证明**：mode.entrance=unavailable 8s → entrance observations 冻结、evidence 增 unavailable 行
  （value_json=null、observed_at=null、retrieved_at=当前）、/api/current 与卡片保持最后成功值
- error 模式：error_message="SIMULATED mode=error"、仍不写 observations/store
- 恢复 ok：双写恢复、最新证据带业务值
- 向后兼容：阶段01 格式信封正常双写；"data 非空+status=error"畸形信封被拒绝不落库
- WS：失败/恢复证据帧实时推送；重启后端后历史与证据仍在、/api/current 从 MQTT 重建
- mode 422 矩阵：blocked/3/多余键 foo 全部 422 且配置不变
- 前端 JS 语法校验通过；页面无"0/2""入口异常"等伪造文本

# AI 会话快照 · 2026-11-06（同日第三次任务：A00 阶段03 显式约束与派生结果）

> 同日第三次开发任务，如实追加记录，不改动前面内容。

## 一、任务

1. 教学配置参数独立 config：capacity=1000、entrance_total=2、support_reference=10（教学参数，非行业标准）
2. 约束计算：remaining_capacity/ratio、entrance_ratio、support_gap/ratio、route_flexibility（normal→normal；limited→reduced）
3. 输入=最新有效业务状态（observations）+ config 参数；输出=结构化派生结果 JSON
4. 只算派生结果，禁止 impact/整体态势/run_id
5. 新增 POST /api/compute-derived；S1/S2 场景测试，改 crowd 必须重新计算

## 二、关键决策

1. **config.json 放仓库根**（官方未定路径，格式 JSON 自选）；**每次计算读取同一份参数**——
   改文件即生效无需重启（实测 capacity 1000→2000 后立即 1700/0.85），避免"页面里另一份写死的 capacity"。
   文件缺失/非法 → ValueError → 接口 500 并说明，绝不静默用默认值。
2. **entrance_ratio 分母取配置 entrance_total**（教学参数单一来源）；分子 available 取输入状态。
3. **响应分层**：config / states / derived 三层 + computed_at，官方要求"原始状态、派生结果、
   最终态势不混层"（本阶段无态势层）；官方示例按 capacity/entrance/support/route 分组——照用。
4. **派生结果不落库**：官方明确持久化是阶段04 runs 的事（"不要提前抢做"），阶段03 只计算+返回+测试。
5. **约束测试文件化**：tests/test_derived.py（7 条，`py -m tests.test_derived` 直跑纯函数层），
   覆盖官方 S1 全量期望、S2 全序列、3.9 现场验证值（crowd=620、support 8→11）、入口 1/2、
   路线映射表、以及一条"响应禁词守卫"（断言响应不含 impact/situation/run_id/态势/影响）。
6. 官方公式逐字采用：support_gap 可为负（官方例证 -2）；main_route 映射仅两条；不 clamp 不解读。

## 三、AI 出错与纠正

1. **后端 --reload 静默失效**：POST /api/compute-derived 返回 405——排查发现 uvicorn 的
   WatchFiles 只响应了 schemas.py 一次，之后对 constraints.py/main.py 的新增完全无感知，
   worker 一直在服务旧路由（catch-all 只收 GET 故返回 405）。纠正：停掉 watcher+worker 树，
   改用不带 --reload 的干净实例重启（代码已稳定，纯进程生命周期更可控），全部测试转绿。
2. constraints.py 初版遗留：未使用的 `ValidationError` 导入 + `json_loads` 间接层——已清理，
   load_config 改为逐层包装异常（文件不可读/非 JSON/字段非法 → 明确的 ValueError 文案）。

## 四、验证结果（全部通过）

- `py -m tests.test_derived`：7/7（S1 期望 700/0.70/1.00/−2/1.20/normal；S2 序列 700→500→350→250
  与 0.70→0.50→0.35→0.25、其余稳定；crowd=620→380/0.38；support 8→11→gap 2→−1、ratio 0.80→1.10）
- 线上端点：S1/S2/现场值全对；422 四连测（crowd<0、main_route="blocked"、available<0、缺字段）
- config 热读：capacity 改 2000 → 1700/0.85 即时生效，已恢复 1000
- 禁词 grep：变更文件仅测试守卫断言命中，无影响/态势/run_id 业务逻辑
